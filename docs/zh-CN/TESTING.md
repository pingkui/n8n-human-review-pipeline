# 测试

## `python3 test.py` 做了什么
它启动 `mock_server.py` 和一个真实的 n8n 容器,导入并发布 `workflow.json`,等到 webhook 注册完成,再像请求方和审核人那样通过 HTTP 驱动工作流,最后清理。结果:**12/12 项检查通过**。

mock 服务充当外部的四样东西,并记录收到的一切(`GET /state`):
| mock 端点 | 充当 |
|---|---|
| `POST /v1/chat/completions` | 模型;返回确定性的草稿(修改版草稿会引用意见);主题里含 "overclaim" 会加入一个没有依据的数字,含 "banned" 会加入一个禁用词 |
| `POST /notify` | 审核渠道 |
| `POST /publish` | CMS |
| `POST /audit` | 审计日志 |

## 12 项检查
| # | 检查 | 证明 |
|---|---|---|
| 1 | 非法输入返回 400 | 错误请求在一开始就被拒绝 |
| 2 | 非法输入不会调用模型 | 也就不花钱 |
| 3 | 合法请求被接受(202)并带请求 id | 异步约定 |
| 4 | 审核人收到草稿、检查结果和恢复链接 | 人拿到了需要的东西 |
| 5 | 批准之前不会发布任何东西 | 等待期间闸门有效 |
| 6 | revise 会触发体现意见的第二版草稿 | 修改循环 |
| 7 | 批准后发布的恰好是被批准的草稿 | 从审核到发布之间文字不会漂移 |
| 8 | 审计记录显示 2 次尝试后已发布,并带审核人 | 可追溯 |
| 9 | 没有依据的数字和禁用词都被标记 | 确定性检查有效 |
| 10 | 被拒绝的草稿绝不会发布 | 拒绝是终局 |
| 11 | 修改次数上限会终止循环且不发布 | 循环有界 |
| 12 | 无法识别的决定不会被当成批准 | 安全的默认值 |

## 一次真实运行(不属于仓库测试)
还用真实模型(Kimi `kimi-k2.6`)和本地部署跑过一个请求:草稿通过了全部四项检查,要求的修改被执行,批准后发布并留下审计。它需要 API 密钥,所以不在 `test.py` 里。

## 没有测试的
- 真实模型输出的质量;mock 是确定性的。
- 真实的审核渠道(Slack、邮件)或真实的 CMS。
- 并发:同时有很多个待审核,或同一个恢复链接被回复两次。
- 模型、通知或发布调用失败(见 `ARCHITECTURE.md` 里的已知缺口)。
- 有执行在等待时 n8n 重启之后的行为。

## 新增检查或用例
- 新的草稿检查:在 `build_workflow.py` 里 `Check draft` 代码的 `checks` 列表中加一项,重新运行 `python3 build_workflow.py`,并在 `mock_server.py` 里加一个触发条件(主题里的关键词,让假草稿违反它),再在 `test.py` 里加一个用例。
- 新的客户档案:见 `EXTENDING.md`。
- 始终通过 `build_workflow.py` 重新生成 `workflow.json`,不要手改 JSON。
